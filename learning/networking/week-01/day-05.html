TCP, UDP, DNS and DHCP

Week 01 · Day 05

Deep understanding of TCP, UDP, DNS, DHCP, transport-layer communication, network services, packet analysis and troubleshooting

جلسه پنجم: TCP، UDP، DNS و DHCP

هدف این جلسه صرفاً حفظ کردن شماره پورت‌ها یا مراحل Handshake نیست. هدف این است که بتوانی ارتباط میان برنامه‌ها، انتقال داده، Name Resolution و تخصیص خودکار تنظیمات شبکه را تحلیل و مشکلات واقعی این سرویس‌ها را عیب‌یابی کنی.

1. اهداف یادگیری

در پایان این جلسه باید بتوانید:

  • تفاوت TCP و UDP را از نظر عملکرد و کاربرد توضیح دهید.
  • فرآیند TCP Three-Way Handshake را تحلیل کنید.
  • نقش TCP Flags، Sequence Number و Acknowledgment Number را بشناسید.
  • مفهوم Port و Socket را در ارتباطات شبکه توضیح دهید.
  • فرآیند DNS Resolution و انواع رکوردهای DNS را درک کنید.
  • مراحل DHCP DORA را توضیح دهید.
  • با PowerShell وضعیت ارتباطات TCP، تنظیمات DNS و DHCP را بررسی کنید.
  • ترافیک TCP، UDP، DNS و DHCP را در Wireshark تحلیل کنید.
  • مشکلات رایج ارتباطات شبکه را عیب‌یابی کنید.

2. جایگاه پروتکل‌ها در مدل TCP/IP

تا اینجا با Ethernet، MAC Address، ARP و IPv4 آشنا شدیم. حالا باید ببینیم برنامه‌های کامپیوتری چگونه با یکدیگر ارتباط برقرار می‌کنند.

در مدل TCP/IP، پروتکل‌های TCP و UDP در لایه Transport قرار می‌گیرند.

DNS و DHCP نیز سرویس‌های مهم لایه Application هستند که برای انتقال پیام‌هایشان از پروتکل‌های Transport استفاده می‌کنند.

Protocol Main Function Transport
TCP Reliable communication TCP
UDP Datagram delivery UDP
DNS Name resolution Usually UDP, also TCP
DHCP Automatic IP configuration UDP

نکته مهم: DNS و DHCP خودشان پروتکل‌های لایه کاربرد هستند، اما برای انتقال پیام‌هایشان از UDP یا TCP استفاده می‌کنند.

مسیر یک ارتباط

وقتی یک برنامه می‌خواهد با یک سرور ارتباط برقرار کند، معمولاً این مراحل اتفاق می‌افتند:

  1. برنامه مقصد را با نام دامنه مشخص می‌کند.
  2. سیستم با DNS آدرس IP مقصد را پیدا می‌کند.
  3. سیستم با استفاده از IP و Port مقصد، ارتباط را برقرار می‌کند.
  4. TCP یا UDP داده را منتقل می‌کند.
  5. IP و Ethernet اطلاعات را برای انتقال در شبکه آماده می‌کنند.

3. TCP چیست؟

TCP مخفف Transmission Control Protocol است.

TCP یک پروتکل Connection-Oriented است. یعنی قبل از انتقال داده، دو طرف ارتباط یک اتصال منطقی برقرار می‌کنند.

TCP تلاش می‌کند داده‌ها را به‌صورت قابل اعتماد، مرتب و بدون تحویل تکراری به برنامه مقصد برساند.

ویژگی‌های TCP

  • Connection-Oriented
  • Reliable Delivery
  • Ordered Delivery
  • Error Detection
  • Retransmission
  • Flow Control
  • Congestion Control
  • Full-Duplex Communication

TCP چگونه قابل اعتماد است؟

فرض کنید یک فایل 100 مگابایتی از کامپیوتر A به سرور B ارسال می‌کنید.

TCP داده را به بخش‌هایی تقسیم می‌کند. هر بخش دارای اطلاعات کنترلی است.

گیرنده با استفاده از شماره‌های Sequence و Acknowledgment می‌تواند مشخص کند چه داده‌ای دریافت شده است.

اگر بخشی از داده گم شود، TCP می‌تواند آن را دوباره ارسال کند.

توجه کنید TCP تضمین نمی‌کند که شبکه هیچ Packet Loss نداشته باشد. بلکه مکانیزم‌هایی دارد که با Loss مقابله می‌کنند.

4. TCP Three-Way Handshake

قبل از انتقال داده در یک اتصال TCP معمولی، سه مرحله برای برقراری اتصال انجام می‌شود.

مرحله اول: SYN

Client یک Segment با Flag برابر SYN به Server می‌فرستد.

Client در این پیام اعلام می‌کند که می‌خواهد یک اتصال TCP برقرار کند.

مرحله دوم: SYN-ACK

Server درخواست را دریافت می‌کند و در صورت پذیرش، Segment دارای دو Flag زیر را ارسال می‌کند:

  • SYN
  • ACK

Server با این پیام هم درخواست Client را تأیید می‌کند و هم اطلاعات شروع ارتباط خودش را اعلام می‌کند.

مرحله سوم: ACK

Client پیام Server را دریافت می‌کند و یک ACK ارسال می‌کند.

پس از تکمیل Handshake، ارتباط TCP برقرار شده است و انتقال داده می‌تواند آغاز شود.

خلاصه Handshake

Step Sender Flags
1 Client → Server SYN
2 Server → Client SYN, ACK
3 Client → Server ACK

چرا سه مرحله لازم است؟

این فرآیند به دو طرف اجازه می‌دهد ارتباط را هماهنگ کنند و شماره‌های اولیه Sequence را مبادله کنند.

این کار به شناسایی ارتباط معتبر و آماده‌سازی انتقال داده کمک می‌کند.

5. TCP Flags

TCP Header دارای Flagهایی است که وضعیت و هدف یک Segment را مشخص می‌کنند.

Flag Meaning
SYN شروع و هماهنگی اتصال
ACK تأیید دریافت داده یا اطلاعات کنترلی
FIN درخواست پایان منظم اتصال
RST قطع یا رد فوری اتصال
PSH درخواست تحویل سریع‌تر داده به برنامه
URG نشان‌دهنده وجود داده فوری
ECE علامت‌گذاری اطلاعات مربوط به ECN
CWR اعلام واکنش فرستنده به ازدحام ECN

SYN Flood چیست؟

در حمله SYN Flood، مهاجم تعداد زیادی درخواست SYN ارسال می‌کند، اما Handshake را کامل نمی‌کند.

در نتیجه منابع Server ممکن است درگیر اتصال‌های نیمه‌باز شوند.

روش‌های دفاعی می‌توانند شامل موارد زیر باشند:

  • SYN Cookies
  • Firewall Rules
  • Rate Limiting
  • DDoS Protection
  • Monitoring Connection States

پایان ارتباط TCP

TCP معمولاً با استفاده از FIN و ACK اتصال را به‌صورت کنترل‌شده می‌بندد.

در حالت معمول، هر سمت ارتباط می‌تواند جریان ارسال داده خودش را جداگانه خاتمه دهد.

RST برای قطع ناگهانی یا رد اتصال استفاده می‌شود.

6. Sequence Number و Acknowledgment Number

TCP برای مدیریت جریان داده از شماره‌های Sequence و Acknowledgment استفاده می‌کند.

Sequence Number

این شماره موقعیت داده در جریان بایت‌های TCP را مشخص می‌کند.

Acknowledgment Number

این شماره معمولاً نشان می‌دهد گیرنده انتظار دارد بایت بعدی از چه موقعیتی دریافت شود.

مثال ساده:

فرض کنید Client داده‌ای ارسال می‌کند که از Sequence Number برابر 1000 شروع می‌شود و 500 بایت دارد.

در صورت دریافت صحیح، گیرنده می‌تواند Acknowledgment Number برابر 1500 را اعلام کند.

یعنی بایت‌های تا قبل از 1500 دریافت شده‌اند و گیرنده منتظر بایت بعدی است.

نکته فنی

TCP معمولاً از Cumulative Acknowledgment استفاده می‌کند. در صورت فعال بودن قابلیت‌هایی مانند SACK، گیرنده می‌تواند اطلاعات دقیق‌تری درباره بخش‌های دریافت‌شده ارائه دهد.

7. TCP Flow Control و Congestion Control

این دو مفهوم شبیه به هم نیستند.

Flow Control

Flow Control از گیرنده محافظت می‌کند.

اگر گیرنده سرعت پردازش داده کمتری داشته باشد، می‌تواند با استفاده از Receive Window به فرستنده اعلام کند چه مقدار داده دیگر می‌تواند دریافت کند.

Congestion Control

Congestion Control برای جلوگیری از فشار بیش از حد به شبکه استفاده می‌شود.

TCP با مکانیزم‌هایی مانند موارد زیر وضعیت ارسال را مدیریت می‌کند:

  • Congestion Window
  • Slow Start
  • Congestion Avoidance
  • Fast Retransmit
  • Fast Recovery
Mechanism Protects
Flow Control Receiver
Congestion Control Network

8. UDP چیست؟

UDP مخفف User Datagram Protocol است.

UDP یک پروتکل Connectionless است.

برخلاف TCP، قبل از ارسال داده نیازی به Three-Way Handshake ندارد.

UDP داده‌ها را در قالب Datagram ارسال می‌کند.

ویژگی‌های UDP

  • Connectionless
  • بدون تضمین تحویل
  • بدون تضمین ترتیب دریافت
  • بدون مکانیزم Retransmission داخلی
  • سربار کم
  • مناسب برای ارتباطات حساس به تأخیر

UDP در صورت نیاز به مکانیزم‌های اطمینان از تحویل، این قابلیت‌ها را به پروتکل یا برنامه بالاتر واگذار می‌کند.

کاربردهای UDP

  • DNS
  • DHCP
  • VoIP
  • Online Gaming
  • Live Streaming
  • NTP
  • برخی ارتباطات VPN

مقایسه TCP و UDP

Feature TCP UDP
Connection Connection-Oriented Connectionless
Handshake Yes No
Reliability Built-in mechanisms No delivery guarantee
Ordering Yes No guarantee
Retransmission Yes No built-in retransmission
Header Minimum 20 bytes 8 bytes
Flow Control Yes No built-in flow control
Typical Use Web, SSH, File Transfer DNS, DHCP, Real-time traffic

نکته: UDP لزوماً همیشه سریع‌تر از TCP نیست. عملکرد واقعی به نوع برنامه، شبکه و شرایط ارتباط بستگی دارد.

9. Port Numbers و Socket

آدرس IP مشخص می‌کند داده به کدام Host برسد.

Port Number مشخص می‌کند داده به کدام سرویس یا Endpoint در آن Host تحویل داده شود.

مثلاً:

  • IP Address: 192.168.1.10
  • TCP Port: 443

این ترکیب نشان می‌دهد که ارتباط با سرویس HTTPS روی میزبان موردنظر برقرار می‌شود.

توجه: بعضی سرویس‌های مدرن می‌توانند از Transport یا Portهای دیگری هم استفاده کنند. جدول بالا Portهای رایج را نشان می‌دهد.

Socket چیست؟

Socket یک Endpoint ارتباطی است.

در ارتباطات IP، ترکیبی از آدرس IP، Port و نوع پروتکل به شناسایی ارتباط کمک می‌کند.

یک TCP Connection معمولاً با این چهار مقدار شناسایی می‌شود:

  • Source IP
  • Source Port
  • Destination IP
  • Destination Port

به این مجموعه Four-Tuple می‌گویند.

10. DNS چیست؟

DNS مخفف Domain Name System است.

DNS نام دامنه را به اطلاعاتی مانند آدرس IP تبدیل می‌کند.

انسان‌ها معمولاً نام‌هایی مانند example.com را به خاطر می‌سپارند، اما برای برقراری ارتباط شبکه‌ای به آدرس IP نیاز داریم.

DNS این فاصله را پر می‌کند.

فرآیند DNS Resolution

فرض کنید مرورگر می‌خواهد به example.com متصل شود.

  1. سیستم ابتدا ممکن است Cache محلی را بررسی کند.
  2. اگر پاسخ موجود نباشد، درخواست به DNS Resolver ارسال می‌شود.
  3. Resolver ممکن است Cache خودش را بررسی کند.
  4. در صورت نیاز، Resolver سراغ Root DNS Server می‌رود.
  5. Root Server اطلاعات مربوط به TLD را معرفی می‌کند.
  6. TLD Server آدرس Authoritative Name Server را معرفی می‌کند.
  7. Authoritative Server پاسخ نهایی را ارائه می‌دهد.
  8. Resolver پاسخ را به Client برمی‌گرداند.

در عمل، Resolver ممکن است از Cache استفاده کند و تمام مراحل بالا در هر درخواست تکرار نمی‌شوند.

Recursive و Iterative Query

Recursive Query:

Client از DNS Resolver درخواست پاسخ نهایی می‌کند. Resolver مسئول پیدا کردن پاسخ است یا خطا را برمی‌گرداند.

Iterative Query:

سرور DNS ممکن است به‌جای پاسخ نهایی، آدرس سرور دیگری را معرفی کند که اطلاعات بیشتری دارد.

DNS Cache

DNS برای کاهش تأخیر و بار شبکه از Cache استفاده می‌کند.

هر رکورد DNS معمولاً دارای TTL است.

TTL مشخص می‌کند اطلاعات تا چه مدت می‌توانند در Cache معتبر در نظر گرفته شوند.

11. انواع DNS Records

DNS فقط برای تبدیل نام به IPv4 نیست.

رکوردهای متنوعی برای اهداف مختلف وجود دارند.

Record Purpose Example
A نام به IPv4 example.com → IPv4
AAAA نام به IPv6 example.com → IPv6
CNAME Alias www → example.com
MX Mail Server mail.example.com
NS Name Server ns1.example.com
TXT Text Information SPF / Verification
PTR Reverse DNS IP → Hostname
SOA Zone Information Primary DNS / Serial
SRV Service Location Service / Port

Forward Lookup

تبدیل نام دامنه به آدرس IP.

Reverse Lookup

تبدیل آدرس IP به نام میزبان با استفاده از PTR Record.

DNS over HTTPS و DNS over TLS

در DNS سنتی، درخواست‌ها معمولاً به شکل رمزنگاری‌نشده ارسال می‌شوند.

DoH درخواست DNS را در HTTPS منتقل می‌کند.

DoT از TLS برای رمزنگاری ارتباط DNS استفاده می‌کند.

این روش‌ها می‌توانند حریم خصوصی مسیر بین Client و Resolver را بهبود دهند، اما به‌تنهایی همه مشکلات امنیتی DNS را حل نمی‌کنند.

DNS over TCP

DNS فقط UDP نیست.

DNS از UDP و TCP روی Port 53 استفاده می‌کند.

TCP می‌تواند برای پاسخ‌های بزرگ، Zone Transfer و شرایطی که انتقال قابل اعتماد لازم است استفاده شود.

12. DHCP چیست؟

DHCP مخفف Dynamic Host Configuration Protocol است.

DHCP به دستگاه‌ها اجازه می‌دهد تنظیمات شبکه را به‌صورت خودکار دریافت کنند.

بدون DHCP، مدیر شبکه باید اطلاعاتی مانند IP و Subnet Mask را برای هر دستگاه به‌صورت دستی تنظیم کند.

DHCP چه اطلاعاتی ارائه می‌دهد؟

  • IP Address
  • Subnet Mask
  • Default Gateway
  • DNS Server
  • Lease Duration
  • Domain Name
  • سایر Optionهای پیکربندی

DHCP DORA

فرآیند اصلی دریافت آدرس IPv4 از DHCP Server با چهار مرحله شناخته می‌شود:

مرحله اول: Discover

Client هنوز IP معتبر ندارد.

برای پیدا کردن DHCP Server یک DHCP Discover ارسال می‌کند.

در حالت معمول:

  • Source IP: 0.0.0.0
  • Destination IP: 255.255.255.255
  • Source UDP Port: 68
  • Destination UDP Port: 67

مرحله دوم: Offer

DHCP Server یک پیشنهاد شامل IP و تنظیمات شبکه ارسال می‌کند.

مرحله سوم: Request

Client اعلام می‌کند که پیشنهاد موردنظر را می‌پذیرد.

مرحله چهارم: Acknowledgment

DHCP Server درخواست را تأیید می‌کند و Lease را اختصاص می‌دهد.

پس از تکمیل فرآیند، Client می‌تواند از تنظیمات اختصاص‌یافته استفاده کند.

DHCP Lease

آدرس DHCP معمولاً برای یک بازه زمانی مشخص اختصاص داده می‌شود.

این بازه Lease Time نام دارد.

Client پیش از پایان Lease تلاش می‌کند آن را تمدید کند.

در رفتار استاندارد DHCPv4:

  • T1 معمولاً در 50 درصد Lease Time است.
  • T2 معمولاً در 87.5 درصد Lease Time است.

این زمان‌ها مقادیر پیش‌فرض رایج هستند و ممکن است بر اساس شرایط یا تنظیمات متفاوت باشند.

DHCP Relay

در شبکه‌های مختلف، DHCP Broadcast به‌صورت معمول از Router عبور نمی‌کند.

اگر DHCP Server در Subnet دیگری باشد، می‌توان از DHCP Relay Agent استفاده کرد.

در Cisco IOS معمولاً از دستور زیر استفاده می‌شود:

ip helper-address 192.168.10.10

این دستور روی Interface مربوط به شبکه Client تنظیم می‌شود و درخواست‌های DHCP را به Server مشخص‌شده Relay می‌کند.

13. DHCP و DNS در کنار یکدیگر

DHCP و DNS دو سرویس متفاوت هستند، اما در شبکه‌های سازمانی به‌شدت با یکدیگر همکاری می‌کنند.

DHCP به Client آدرس IP و DNS Server را معرفی می‌کند.

DNS نام دستگاه‌ها و سرویس‌ها را به اطلاعات شبکه تبدیل می‌کند.

مثال:

  1. لپ‌تاپ به شبکه متصل می‌شود.
  2. DHCP به آن IP برابر 192.168.1.100 اختصاص می‌دهد.
  3. DHCP آدرس Gateway و DNS Server را نیز ارائه می‌کند.
  4. کاربر آدرس intranet.company.local را وارد می‌کند.
  5. Client از DNS برای پیدا کردن IP سرور استفاده می‌کند.
  6. ارتباط با سرور برقرار می‌شود.

16. Troubleshooting سناریومحور

Scenario 1: کاربر IP دارد اما سایت‌ها باز نمی‌شوند

احتمال‌ها:

  • DNS Server در دسترس نیست.
  • DNS Record اشتباه است.
  • Gateway مشکل دارد.
  • ارتباط TCP به مقصد برقرار نمی‌شود.
  • Firewall ترافیک را مسدود کرده است.

روش بررسی:

ipconfig /all
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443

Scenario 2: سایت با IP باز می‌شود اما با Domain باز نمی‌شود

احتمال زیاد مشکل در DNS Resolution است.

بررسی کنید:

Resolve-DnsName example.com

سپس DNS Cache را بررسی کنید:

Get-DnsClientCache

Scenario 3: کامپیوتر IP برابر 169.254.x.x گرفته است

این محدوده Link-Local است.

در Windows، آدرس‌دهی خودکار از این محدوده معمولاً APIPA نامیده می‌شود.

این وضعیت می‌تواند نشان دهد Client نتوانسته از DHCP یک آدرس دریافت کند.

موارد بررسی:

  • DHCP Server روشن است؟
  • DHCP Scope آدرس آزاد دارد؟
  • VLAN درست است؟
  • DHCP Relay تنظیم شده است؟
  • مسیر شبکه تا DHCP Server برقرار است؟

Scenario 4: TCP Connection Failed

دستور:

Test-NetConnection 192.168.1.10 -Port 443

موارد احتمالی:

  • سرویس مقصد اجرا نیست.
  • Port در حال Listen نیست.
  • Firewall ترافیک را Block می‌کند.
  • Routing اشتباه است.
  • مسیر شبکه قطع شده است.

Scenario 5: DNS Query Timeout

بررسی کنید:

  • آیا DNS Server قابل دسترس است؟
  • آیا UDP Port 53 مسدود شده؟
  • آیا TCP Port 53 در شرایط لازم قابل دسترس است؟
  • آیا DNS Server پاسخ صحیح می‌دهد؟
  • آیا تنظیمات DNS Client درست هستند؟

17. Network Automation و کاربرد در دنیای واقعی

یک Network Automation Engineer باید بتواند وضعیت سرویس‌های شبکه را به‌صورت خودکار بررسی کند.

چند نمونه از کارهای قابل اتوماسیون:

DNS Monitoring

  • بررسی دوره‌ای DNS Resolution
  • مقایسه پاسخ چند DNS Server
  • ثبت زمان پاسخ
  • تشخیص خطای Name Resolution

TCP Monitoring

  • بررسی Portهای حیاتی
  • شناسایی Connectionهای غیرعادی
  • بررسی وضعیت سرویس‌ها
  • ثبت Connectionهای ناموفق

DHCP Monitoring

  • بررسی Scopeهای دارای ظرفیت کم
  • شناسایی آدرس‌های نامعتبر
  • پایش Leaseها
  • تشخیص DHCP Serverهای ناشناس

نمونه ساده Health Check در PowerShell

$targets = @(
    @{ Name = "DNS"; Host = "1.1.1.1"; Port = 53 },
    @{ Name = "HTTPS"; Host = "example.com"; Port = 443 },
    @{ Name = "SSH"; Host = "github.com"; Port = 22 }
)

foreach ($target in $targets) {
    $result = Test-NetConnection `
        -ComputerName $target.Host `
        -Port $target.Port `
        -WarningAction SilentlyContinue

    [PSCustomObject]@{
        Service = $target.Name
        Host    = $target.Host
        Port    = $target.Port
        Status  = if ($result.TcpTestSucceeded) { "Online" } else { "Failed" }
    }
}

این نمونه برای تست TCP است. بررسی DNS و UDP به روش‌های مخصوص خود نیاز دارند.

چرا این مهارت مهم است؟

در شبکه‌های سازمانی، بررسی دستی ده‌ها یا صدها سرویس زمان‌بر است.

Automation به مهندس شبکه کمک می‌کند وضعیت سرویس‌ها را سریع‌تر بررسی کند، خطاها را ثبت کند و برای تحلیل‌های بعدی داده جمع‌آوری کند.

19. چالش پایانی هفته اول

فرض کنید یک شرکت کوچک دارای 30 کارمند است.

کاربران گزارش می‌دهند:

  • بعضی کامپیوترها IP دریافت نمی‌کنند.
  • بعضی کاربران می‌توانند با IP به سرور متصل شوند، اما با نام دامنه نه.
  • اتصال HTTPS به یک سرویس داخلی برقرار نمی‌شود.
  • مدیر شبکه می‌خواهد وضعیت Portهای حیاتی را به‌صورت خودکار بررسی کند.

وظایف شما

  1. برای مشکل دریافت IP، مسیر عیب‌یابی DHCP را طراحی کنید.
  2. توضیح دهید چگونه مشکل DNS را از مشکل Routing تشخیص می‌دهید.
  3. با PowerShell اتصال TCP به Port 443 را بررسی کنید.
  4. توضیح دهید در Wireshark چگونه DHCP DORA را مشاهده می‌کنید.
  5. یک Health Check ساده برای سه سرویس طراحی کنید.

هدف این چالش حفظ کردن دستورها نیست. باید بتوانید از روی نشانه‌ها، لایه و سرویس مشکل‌دار را پیدا کنید.

20. اشتباهات رایج

  1. تصور اینکه UDP همیشه سریع‌تر از TCP است؛ عملکرد واقعی به شرایط شبکه و نوع برنامه وابسته است.
  2. تصور اینکه DNS فقط از UDP استفاده می‌کند؛ DNS می‌تواند از TCP نیز استفاده کند.
  3. اشتباه گرفتن UDP Port 67 و 68؛ Server از 67 و Client از 68 استفاده می‌کند.
  4. تصور اینکه دریافت آدرس 169.254.x.x به معنی دریافت IP از DHCP Server است؛ این آدرس معمولاً Link-Local و حاصل APIPA است.
  5. تصور اینکه موفقیت TCP Handshake به معنی سالم بودن کامل Application است.
  6. اشتباه گرفتن Flow Control با Congestion Control؛ اولی از Receiver و دومی از شبکه محافظت می‌کند.
  7. تصور اینکه Acknowledgment Number شماره آخرین بایت دریافت‌شده است؛ معمولاً شماره بایت بعدی مورد انتظار را نشان می‌دهد.
  8. تصور اینکه هر DNS Query الزاماً باید به Root DNS Server برسد؛ Cache می‌تواند بسیاری از مراحل را حذف کند.
  9. تصور اینکه DHCP Broadcast بدون Relay از Router عبور می‌کند.
  10. فرض اینکه موفقیت Test-NetConnection روی Port 443 به معنی سالم بودن کامل HTTPS است؛ این تست فقط برقراری TCP را بررسی می‌کند. ## 21. منابع و مطالعه بیشتر
